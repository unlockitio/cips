# Candidate Daml interfaces

This project contains the directly consultable candidate interface source for the CIP. It is not a complete credential or registry implementation. In particular, concrete templates, signatories, issuer revocation, registry removal, and generic registration expiry behavior remain unresolved; concrete deployment profiles may define those policies. The generic `Credential` interface standardizes holder self-removal as a consuming choice, but an implementing template or profile must construct the concrete replacement through the abstract implementation method and satisfy its own signatory, observer, and authorization rules. A holder-controlled interface exercise does not authorize creation under arbitrary template signatories, so this candidate project does not invent an issuer or signatory model.

Every `CredentialSubject` has `id : Optional W3C_VC_Identifier`. `Some identifier` serializes as `credentialSubject.id`; `None` omits that property, may still carry claims, and does not guarantee anonymity. Validation and identifier mapping apply only when the ID is present, and identifier lookup does not match subjects whose IDs are absent. The reserved claim key `id` must be rejected even when the optional ID is absent, and implementations must never infer a missing ID from claims, holders, issuer, or nested values. `CredentialView.issuer` uses the same identifier representation non-optionally while retaining distinct issuer semantics. Use `W3C_VC_Identifier_Party` for a Canton-native identifier; an external W3C serialization profile must define its Party-to-URL-or-DID mapping. Use `W3C_VC_Identifier Text` only for a DID, URI, national identifier, or other external identifier permitted and validated by the applicable profile; the value is not automatically a DID. Profiles should avoid putting raw national identifiers on-ledger or into public serialization unless necessary and authorized. `credentialSubject`, `holders`, and `issuer` are independent: none implies either of the others, and implementations must not infer subjects, holder membership, controllers, or authorization from identifiers, claims, or arbitrary `AnyValue` values.

One logical VC is represented by one canonical `Credential` contract with at least one designated Canton operational holder in `holders : NonEmpty Party`. Concrete templates must reject duplicates and use deterministic Party ordering. The view is not mutated in place. The consuming `Credential_RemoveSelfAsHolder` choice lets a current holder remove exactly itself and delegates replacement construction to `credential_removeSelfAsHolderImpl`. It returns `Credential_RemoveSelfAsHolderResult` with exactly one `replacementCredential : ContractId Credential` whose remaining holders preserve their order. The choice rejects a non-holder and the final holder. The replacement preserves logical credential identity, credential types, issuer, subjects and claims, intrinsic validity, and unrelated profile fields. The interface view does not grant ledger visibility, so templates that expect holders to discover or fetch the credential through normal Daml visibility must make every designated holder a stakeholder, normally an observer. Removed holders lose future stakeholder visibility according to concrete stakeholder behavior, but ledger history and data they already observed cannot be erased. `holders` is excluded from standard W3C VC serialization unless a named extension profile defines it.

For a template that also implements `RegisteredCredential`, self-removal must copy embedded registration metadata unchanged and preserve the registration lifecycle without a gap. Contract-ID references must be updated atomically in the same transaction, or stable logical identity must remain correctly referenced. Timestamps, expiry, fees, status, retention, and audit or history state must not reset. The generic result remains `ContractId Credential`; stronger registered-credential results or discovery are profile-specific. Implementations must not add a second registered self-removal choice that conflicts with or bypasses the base choice.

Relinquishment removes only the exercising holder and replaces the contract; it does not terminate the logical credential. The unchanged `Credential_ArchiveAsAllHolders` choice remains the terminal action jointly authorized by every holder and creates no replacement. Local wallet removal, holder relinquishment, Daml archival, intrinsic expiry, revocation or suspension, registration expiry, and deregistration are distinct. Frequent independently mutable or holder-private relationships may require separate holder-association contracts in a future profile; this candidate does not implement them.

The base interface does not define generic issuer-authorized archival because an external issuer identifier cannot control a Daml choice. A profile or template that needs issuer-authorized archival or revocation must define an explicit Party authorization mechanism and choice. It must not infer that Party from holders, subjects, claims, or external identifier text.

The project uses Daml SDK `3.4.0-rc2`, and the candidate source imports `AnyValue` from `splice-api-token-metadata-v1-1.0.0.dar`. The relative `data-dependencies` path in `daml.yaml` expects that DAR at `../../../canton/unlockit/lib/` from this directory, following the neighboring project's established dependency convention. Profiles or future standardized interfaces may adopt this type or another stable compatible claim-value carrier. Interoperable Daml implementations coordinate the claim-value type and package identity, while serializers and clients agree on external constructor semantics; changing the carrier, constructors, or package identity can require coordinated updates, and structurally similar Daml types are not automatically interchangeable. Consumers in another checkout must configure the selected DAR location. DAR files and build output are intentionally not checked in.

Build from this directory with:

```sh
daml build
```
