# Unified Credentials and DID Canton demo

The default demo runs both products on one local Canton synchronizer and participant, through this directory's `compose.yaml`. It uses one Compose project and network, one PQS pipeline and one PostgreSQL database shared by both products, four Credentials API instances, four DID APIs, a DID BFT reader and a separate Credentials BFT reader. The operator runs `make build && make up` here; do not also start the standalone DID Compose project. That separate project remains an optional legacy isolated demo, not part of the default launch.

The Canton Open Source 3.5.11 container is a minimal local Canton synchronizer: one in-memory `credential-participant`, one local `credential-sequencer`, and one `credential-mediator` in a single process. It is neither an SV nor official LocalNet.

## Versions and artifacts

The `interface`, `model`, and `test` packages use DPM/Daml SDK 3.5.11 and Daml-LF 2.2. The artifact image contains exactly:

- `canton-network-credentials-interfaces-0.2.0.dar`
- `canton-network-credentials-demo-0.1.0.dar`
- `canton-network-credentials-demo-scripts-0.1.0.dar`

Only the interface and model DARs are uploaded. `credential-seed` runs `Seed:main` on a fresh ledger or `Seed:resume` for existing parties from the test DAR. Both call positive fixture builders imported from the CIP #169, #204, #209 and #249 demo test modules: the seed creates 360 deterministic credentials, two registry-issued name credentials, seven scenario credentials and one name holding. The two textual-issuer, holderless examples use a distinct DemoAnchorer Party; the expired-registration example retains intrinsic validity in the future and a registration expiry in the past. Negative test scripts (including duplicate-name and archival cases) run only on isolated test ledgers, never as part of the shared Canton seed. The seeded imported-name example is explicitly unverified demo data. These are demo assertions, not external verification or CIP conformance. The PQS image is pinned to 3.5.8, which provides both the credential reader contract and the DID historical reader signatures. One pipeline projects the participant into one PostgreSQL database that both products read. The DID interface/model DARs are uploaded to this same participant after the Credentials DARs. The Credentials seed runs first; the DID seed allocates or recovers DSO on that participant and reads the already allocated DemoHolderA Party from that participant for its self-claimed Alice alias. It refuses missing parties and will not replace unexpected aliases on rerun. DID assertions are self-claims, not cryptographic verification or name authority.

## Ports and concurrent operation

Container ports are stable service-local ports. Published host ports can be overridden:

| Endpoint | Internal | Default host | Variable |
| --- | ---: | ---: | --- |
| PostgreSQL | `5432` | `15432` | `POSTGRES_PORT` |
| Ledger API | `6865` | `41000` | `LEDGER_PORT` |
| Canton HTTP API and `/livez` | `7575` | `41001` | `CANTON_HTTP_PORT` |
| PQS health | `8080` | `41002` | `PQS_HEALTH_PORT` |
| Credentials API 1–4 | `8080` | `41003`–`41006` | `CREDENTIALS_API_PORT`, `CREDENTIALS_API_2_PORT`–`CREDENTIALS_API_4_PORT` |
| Credentials BFT reader | `8080` | `41007` | `CREDENTIAL_BFT_READER_PORT` |
| DID APIs 1–4 | `8080` | `42003`–`42006` | `DID_API_1_PORT`–`DID_API_4_PORT` |
| BFT reader | `8080` | `42007` | `BFT_READER_PORT` |

There is no second published DID Ledger or Canton HTTP port, no second PostgreSQL and no second PQS health port: both products observe the one participant at `41000` (gRPC) / `41001` (JSON), and both read one shared PQS pipeline writing one `credential-postgres:5432` database published at `15432`. The former `DID_POSTGRES_PORT` (`25432`) and `DID_PQS_HEALTH_PORT` (`42002`) no longer exist. One Compose network connects all services. The project name is `cn-credential-demo`; `make down` affects only its resources. DID service descriptors and the BFT origin map advertise fixed localhost ports 41003 and 42003–42006, so keep those defaults for discovery/E2E.

The single `credential-pqs` pipeline uses `SCRIBE_PIPELINE_FILTER_CONTRACTS: "*"`, so it projects the Credentials and DID interfaces of the same participant into one database. Both products' readers were verified live against that one database: the credential reader contract (`active`/`creates`/`archives` with the 3.5.8 bigint signatures), the DID historical reader signatures and lifecycle columns, and the DID demo alias query over `canton-network-did-demo:Canton.Network.Did.Demo:DemoDidDocument`. The Credentials tag `participant-query-store:3.5.8` and the digest the DID stack pinned resolve to the same image (`sha256:5ece6a0b…`), so one image serves both readers and no separate DID PQS build is needed here.

## Lifecycle

```sh
make build
make up
make smoke-test
make down
```

`make smoke-test` checks Credentials, all four DID APIs, the DID BFT reader, and same-participant cross-product name resolution. Credentials BFT consumer faults are exercised by the reader's local HTTP contract test (`make java-test`); live-stack credentials BFT fault injection is not included. `make seed` reruns both create-if-absent seeds in order. A retained Credentials ledger seeded before DemoAnchorer was introduced is refused by `seed.sh`; use a fresh isolated project with fresh volumes rather than silently changing the signatories of existing contracts. `make down` removes only this project's containers and network and preserves data. `make reset` requires the exact confirmation `RESET-CREDENTIAL-DEMO` and removes this project's volumes. The Canton participant is in-memory, so stopping its container loses ledger state while the PQS database persists. A restarted participant replays from Genesis and PQS refuses to prepend onto a retained datastore, failing with `Cannot prepend to existing datastore`. Relaunching after `make down` therefore requires `make reset` first. `make e2e` owns a disposable stack end to end and removes its own volumes before and after the run; never point it at data you want to retain.

Compose orders both DAR uploads, the Credentials seed and then the DID seed, starts the one PQS pipeline from Genesis, and waits for both products' projection checks against that one database. `make up` starts this dependency graph; `make smoke-test` checks the consumer journey against the already running stack.

Other useful targets are `make daml-build`, `make daml-test`, `make java-test`, `make seed`, `make projection-check`, `make ps`, and the domain-specific log targets.

## Draft Party-profile coverage

The `Cip169ProfileTests` Daml script exercises holder-centric, self-issued and other-issued profile credentials with all 15 draft claim keys. The unassigned `cip-<nr>/` namespace is a fixture placeholder, not an assigned CIP number. The explicit Party subject ID equals the holder because this demo's `CredentialSubject.id` is optional but does not imply the holder when absent. `Cip204GenericPartyProfileTests` preserves the separate generic examples where subject and holder differ.

`Cip169ProfileProjectionTest` tests an application-side projection over registered credential records: holder and namespace filtering, ignored `!subject` suffixes, archival and three validity horizons, registry priority, per-issuer deduplication, full section ordering, well-known key ordering, and compact issuer selection. The projection is a pure consumer example, not a shipped HTTP endpoint. Its tie rule selects the lexicographically greatest contract ID when registry record times match; the draft refers the direction to the Credentials Standard, which has not fixed that direction. The fixture assumes one issuer Party per record, explicit registry priorities, and record times supplied by the caller.

This is not CIP #169 conformance. There is no profile lookup endpoint, DSO registry integration, profile frontend, escaped rendering, or link validation for URI, email, phone, and social handles. The existing `smoke-test.sh` and `e2e.sh` exercise generic credentials and demo names, not a rendered profile. The draft defers precise expiry-boundary semantics and equal-time contract-ID direction to the Credentials Standard; this example makes local choices for both, without asserting them as normative. Profile claims are informational and never identity or name-resolution authority.

## Draft CIP #249 imported-name demonstration

`Cip249ImportedNameTests` demonstrates the Anchor path for DNS-sourced credentials described by draft PR #249, pinned to head `293acf0b53468ae484e267b5928b5746ac580da6`. This is capability evidence, not conformance. The demo maps the draft's publisher (importer registrar party) to `CredentialView.anchorers`, whose members jointly sign; subject to `credentialSubject.id = Some (W3C_VC_Identifier_Party p)`; and holder to `holders = [p]`. The DNS assertion uses external textual issuer `W3C_VC_Identifier "dns"`, a local identifier rather than a specified issuer format. These fields are not identical to a dedicated #249 schema. Six `cprp/*` text claims live in `CredentialSubject.claims`; `cprp/valid-until` duplicates the native `CredentialView.validUntil` and the fixture pairs them consistently. `RegisteredCredentialView.meta` is separate registration metadata and is not used for those claims.

Apex and subdomain FQPNs, all-anchorers signatures, issuer-path rejection, a seven-day encoded interval, and consumer-side expiry are exercised. Demo-local consistency checks reject mismatched DNS method or FQPN network in the consumer fixture, not on the ledger; #249 does not specify those rejection rules. The timestamp fixture pairs text claims with native times supplied by the test. It does not parse or authenticate ISO-8601 claim text, and interval checks do not prove that any re-verification occurred. The ledger accepts an unverified DNS claim: no real DNSSEC resolution, `_canton.<domain>` TXT lookup, ownership proof, registrar governance, multi-attestor verification protocol, trust tier or re-verification scheduler is implemented. The draft is silent about post-issuance verification failure, TXT removal, later DNSSEC failure, and archive/revoke handling of expired credentials; the demo imposes no rules for these.

## External VC structure fixtures

`Cip204ExternalVcShapeTests.daml` models the structures of published [EBSI TU Graz diploma](https://github.com/danubetech/ebsi4austria-examples/blob/eebf4518d3c35bd5b268e01d226695a813520f0f/verifiablecredentials/diploma-tu-graz.jsonld), [MIT Learn OBv3 certificates](https://github.com/digitalcredentials/mit-learn-obv3-template/blob/1c8698751e7e725de41d4a7f268450308bdc1635/certificates/courseCertificate.json), [Privado ID age credential](https://docs.privado.id/docs/js-sdk/js-sdk-example/#output-of-run-command), and [cheqd credentials](https://docs.cheqd.io/product/api-reference/combined/verifiable-credentials). DID issuers and subjects, an absent subject ID, nested and array-valued claims, opaque status and proof data, and a demo-local multiple-subject capability fixture exercise the Anchor path without a Party issuer or holder. Object fields not native to `CredentialView` are stored under demo-local claim keys; optional cheqd evidence and terms are API inputs, not observations from the displayed issued credential. This demonstrates no JSON-LD processing, `@context` resolution, proof verification, status-list evaluation, or W3C VC conformance. Canton anchorer authorization attests to publication only.

The fixtures also exercise every `AnyValue` constructor: typed instants and a narrowed calendar date alongside the published timestamp strings, plus synthetic decimal, seven-day relative time, Canton Party and ledger-local contract-id claims in `typedClaimValueCoverage`. Demo-local `!typed` sibling keys are unrelated to CIP #169's `!subject` convention. Each original external timestamp stays verbatim under its published key because typed `AV_Time` loses lexical details needed to re-serialise the original JSON, including fractional-second digits and offset spelling; typed siblings support time comparisons without pretending to reproduce those bytes. MIT's native validity bounds use the published calendar instants, not runtime test times. The synthetic claims and ledger-local reference are not fields of the four external documents.

## Name as a non-divisible holding

`DemoNameHolding.daml` and `Cip209NameHoldingTests.daml` treat a registry-allocated name as a credential that is simultaneously a CIP-56 token holding, following CIP #209's `NameRecord`, which co-implements `RegistryV1.Credential` and `HoldingV1.Holding` at quantity 1. The real `Splice.Api.Token.HoldingV1.Holding` interface is implemented, projecting a genuine `HoldingView`, not a local record. `scripts/fetch-dependencies.sh` pins `splice-api-token-holding-v1-1.0.0.dar` (SHA-256 `ef75f8eb41a65810221784fdb78bb9dfac7cb22245aba14fa7cb7f69c34e0175`) alongside the metadata DAR, both from `hyperledger-labs/splice` commit `fc5075093d9b10191aeedab66ff35cadaded9dc8`. The template enforces `amount == 1.0`, a canonical name reused from `DemoNames.canonicalName`, an `instrumentId` of the registry administrator plus the canonical name, and `owner` equal to the Party in `credentialSubject.id`. A name must resolve to exactly one answer, and `HoldingView.owner` is a singular Party, so fractional holdings would mean duplicate contracts under one instrument, the duplication #209's 256 shards exist to avoid. Construction is rejected when the subject ID is absent, textual, or names a different Party; `owner` is asserted against the subject, never inferred from the issuer or holders. Rejection labels state intent only, because `submitMustFail` passes for any failure cause.

Corporate structure is layered rather than carved out of the name: the name is one indivisible unit owned by the company Party, equity is a separate `InstrumentId` carrying fractional `Decimal` amounts between shareholders, and control of the owning Party is Canton topology and threshold signing, as in #209's multi-hosted DRO with a `DecentralizedNamespaceDefinition`. `shareSaleDoesNotChangeNameResolution` redistributes equity and asserts the name contract and its owner are unchanged. A lock with several holders demonstrates shared control without division. Because `HoldingView` has no holders field, the credential's `holders` list is carried in holding `meta` under the demo-local `demo.example/holding-holders` key, which is a local carry rather than a standard mapping.

A name cannot be moved by moving the holding. `owner` is pinned to `credentialSubject.id`, and the subject is the issuer's assertion rather than a mutable field, while `TransferFactory_Transfer` is controlled by `transfer.sender` alone and the token standard contains no reference to `Credential` or `RegistryV1`. A raw holding transfer would therefore move `owner` while the credential kept asserting the old subject, a state the template's `ensure` rejects. Name transfer is consequently registry re-issuance: `DemoNameHolding_TransferByReissuance` archives the old contract and creates one whose new credential asserts the new owner, so subject and `owner` move together. The issuer stays load-bearing, since only the registry can re-assert the binding, and holders are irrelevant to ownership: `ownerAndHoldersMoveIndependently` changes holders with `owner` fixed and then `owner` with holders fixed.

Not demonstrated: no executed `TransferFactory_Transfer`, because `TransferFactory` and `TransferInstruction` are interfaces requiring a registry implementation that this demo does not provide; `rawHoldingTransferCannotProduceValidName` executes the structural rejection instead and the transfer-instruction DAR is deliberately not wired. Also absent: split, merge or burn choices (the real `Holding` declares none), lock enforcement or release, allocation flows, any CIP-56 transfer protocol for equity (the redistribution archives and recreates contracts as a demo shortcut), Party topology or threshold signing, and name uniqueness, which remains the registry's off-ledger responsibility.

## API

For seeded GET examples across the Credentials and DID demos, and separately opt-in Canton Ledger API v2 contract commands and auxiliary read-only POST snapshots, import the [Postman collection and local environment](postman/README.md). Same-ledger cross-product agreement is seeded by default and checked by `make smoke-test`.

- `GET /v1/credentials/{credentialId}`
- `GET /v1/credentials?page=0&pageSize=50`
- `GET /v1/registered-credentials/{credentialId}`
- `GET /v1/registered-credentials?page=0&pageSize=50`
- `GET /v1/credential-registries?page=0&pageSize=50`
- `GET /v1/credential-registries/{registryId}`
- `GET /v1/resolve?name=alice.canton&network=localnet&source=credential`
- `GET /v1/reverse-resolve?party=<Party ID>&network=localnet&source=credential`
- `GET /q/health/live`
- `GET /q/health/ready`

Ports 41003–41006 expose four logical Credentials API instances, all reading the same PQS database and Canton participant. Each DID instance on ports 42003–42006 forwards the name routes to its correspondingly numbered Credentials instance through `CREDENTIALS_RESOLUTION_URL`. Port 41007 exposes the separate Credentials quorum reader `GET /v1/bft/credentials/{credentialId}`. It requires three of four matching complete validated intrinsic credential responses (including lifecycle and flattened Canton roles), or three validated `{"error":"credential not found"}` 404s; four comparable split responses return 409, fewer than three agreeing comparable responses return 503, and an operation deadline returns 504. This is read comparison only: shared PQS and Canton are common failure domains, not independent consensus or a credential issue write quorum. The DID name proxy routes are not quorum-read by this reader. No extra Canton network is created. The standalone DID project has no Credentials backend and does not advertise the name services. The two name endpoints demonstrate a scoped variant of draft CIP #171, not compliance: `/v1` replaces its `/v0`, `source` is nonstandard, and `demo` is a local example resolver, not a CIP-registered naming system. Their separate [OpenAPI contract](java-api/resolution-openapi.yaml) retains the required `name`/`party` and `network` arguments and the `fqpn`, `party_id`, `display_name` response fields. Set `CREDENTIALS_NETWORK` to one of `mainnet`, `testnet`, `devnet`, or `localnet` (default `localnet`); requests for another network fail with 400. Omitted `source` defaults to `credential`; other values return 400. Only active, currently valid `DemoPartyName` credentials with a `demo.example/name` text claim and an explicit Party `credentialSubject.id` are considered. Issuer and holder never substitute for subject ID. A forward miss returns 404, multiple eligible bindings return 409; reverse returns an array (possibly empty) and rejects duplicate names with 409. `valid_until` reflects the credential validity horizon; registration expiry is separate. The seed approves `alice.canton` and `bob.canton` for `DemoHolderA` and `DemoHolderB` through `DemoNameRequest`, each with its subject Party explicitly present; the seed checks for an existing credential first, because name uniqueness is the registry's off-ledger responsibility and the ledger does not refuse a second approval. The demo does not prove public naming authority or trusted DNS/CNS registration.

`source=did` additionally requires an agreeing self-claimed alias from the DID API on this same participant, read through the bounded `GET /v1/demo-name-assertions` lookup configured in `CREDENTIALS_DID_ASSERTIONS_URL`. A DID `alsoKnownAs`-style alias is an explicitly self-claimed discovery hint, never a unique allocation or proof of ownership: any DID may claim any alias, including one already claimed or naming a Party it does not control. The registry-allocated name credential therefore remains the only authority. Forward resolution returns 200 only when exactly one DID alias and the single active allocation name the same Party. It returns 409 when the alias names a different Party than the allocation and when conflicting duplicate aliases exist, and 404 when the name is unallocated or unasserted; it never silently falls back to `credential`. Reverse resolution applies the same agreement rule and returns only the allocated names that a self-claim for that exact Party also asserts; claims about other Parties never add or replace names. Without `CREDENTIALS_DID_ASSERTIONS_URL` the capability is absent and `source=did` returns 422; a configured but unreachable or unusable source returns 503. The canonical alias value is the CIP #171 fully qualified party name carried as a `urn:fqpn:<network>:<resolver>:<name>` URI, because DID Core `alsoKnownAs` values are URIs rather than bare names.

Both credential collections support `state=active|archived|all`, four effective-time bounds (`createdFrom`, `createdUntil`, `archivedFrom`, `archivedUntil`), `issuer`, `holder`, `credentialSubjectId`, and literal claim `keyPrefix`; registered credentials additionally support `registryAdmin`. From bounds are inclusive, Until bounds exclusive. `keyPrefix` matches claim keys within a single `CredentialSubject`, and combined with `credentialSubjectId` both must hold on the same subject, so a subject in one credential never matches a claim key carried by a different subject. Ledger archival is independent of semantic validity or registry expiry.

The API uses only PQS 3.5 public snapshot readers through prepared JDBC statements. Fresh pages capture a bigint snapshot; responses include `snapshotOffset` and `nextPageToken`. Repeat filters and pageSize with a token: token alone continues by keyset, token plus page jumps within the same snapshot. Fresh page requests choose a new snapshot. Tokens expire after `CREDENTIALS_PAGINATION_TTL_SECONDS` (900 by default); configure a shared `CREDENTIALS_PAGINATION_SECRET` of at least 32 UTF-8 bytes. Compose's fallback secret is for local demos only.

Singular `active` lookup rejects duplicate active IDs with 409. `archived` returns the latest creation position; `all` prefers active and otherwise the latest archived record. Missing records return 404; invalid filters/tokens or unavailable snapshots return 400; PQS failures return 503. Registry-list offset pagination and separate unsupported event-history endpoints are unchanged.
