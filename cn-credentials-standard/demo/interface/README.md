# Candidate Daml interfaces

This project contains the directly consultable candidate interface source for the CIP. It standardizes a base credential, an optional intrinsic lifecycle capability, registration metadata, holder-authorized removal and archival, initial issuance, and renewal. Concrete credential signatories concatenate nonempty `anchorers` followed by `holders`, which may be empty; entries within each list MUST be unique and duplicates are rejected. Roles are independent; an external textual issuer need not be a Party. Anchoring does not prove an issuer signature or the truth of claims.

The generic `Credential` interface retains holder self-removal and all-holder archival. `Credential_RemoveSelfAsHolder` consumes the canonical contract and creates exactly one replacement without the exercising holder. It rejects non-holders but permits final-holder removal, leaving an empty holder list and unchanged nonempty anchorers. The replacement preserves all other credential fields and, when registered, all registration fields. `Credential_ArchiveAsAllHolders` is terminal and controlled by every holder, falling back to anchorers when holderless. `Credential_ArchiveAsAnchorers` is independently available. Neither choice has an empty controller set.

Natural expiry after `CredentialView.validUntil` is derived and requires no ledger transaction. The generic model defines no status or lineage fields and no generic reissue, suspend, resume, revoke, explicit-expiry, refresh, deregistration, retention-update, `ApplyUpdates`, or `Update` choices.

`CredentialLifecycle requires Credential` is an optional capability. Its consuming `CredentialLifecycle_Renew` choice is anchorer-authorized and replaces the current credential with one whose `validUntil` is strictly later. An absent `validUntil` is unbounded and cannot be renewed to a finite time through this choice. The registered demo template rejects this base choice: anchorer-only exercise cannot silently continue its registration on a successor. Registered intrinsic renewal instead requires explicit registry authorization and changes only `validUntil`.

`RegisteredCredential requires Credential` only and is registration-only; registration does not make lifecycle support mandatory. `RegisteredCredentialLifecycle` requires `RegisteredCredential`, `CredentialLifecycle`, and `Credential`. The final `Credential` is implied by both parent interfaces but must be listed for Daml's transitive requirement closure. Its separate consuming candidate choices target the exact current credential view: `RegisteredCredentialLifecycle_Renew` advances only intrinsic `validUntil` and preserves the entire registration; `RegisteredCredentialLifecycle_ExtendRegistration` advances only registry `expiresAt` and preserves the entire credential view and all other registration fields. Both reject absent expiry in the field they advance but do not require the other expiry. The reference demo uses anchorers followed by `registryAdmin` as controllers and retains anchorer-and-holder replacement signatories. A Daml probe confirms an explicitly admin-controlled consuming choice can create a signed successor even when the admin is only an observer; observer status alone does not grant choice control, and admin-only control is not adopted here. Joint control is a conservative candidate for registration continuity, not a Daml requirement or final DSO governance policy. The demo implements all four interfaces; consumers must rebuild and vet the version 0.2.0 interface DAR because adding an interface method and choice changes its package ID and is not binary-compatible with the previous 0.1.0 package. The `Canton.Network.Credentials.V1` module name remains a candidate source label, not a compatibility guarantee.

`CredentialRegistryFactory_Issue` requires the credential anchorers plus the proposed holders plus the issuer Party, checks the registry administrator against the factory, creates one registered credential, and leaves the factory active. It does not require the credential anchorers to equal the factory anchorers, so one factory serves credentials with arbitrary anchorers; registry acceptance policy belongs to the deployment profile. `CredentialRegistryFactory_Anchor` is the textual-issuer counterpart and never uses textual issuer identity as a controller.

A `W3C_VC_Identifier_Party` issuer must be among `anchorers`, so it is a signatory. The concrete templates enforce this in their creation precondition, which means a Canton Party cannot be named as issuer without its own authorization even when the credential is created directly rather than through the factory.

`Credential_PublicFetch` returns the current `CredentialView` and `RegisteredCredential_PublicFetch` returns both the credential and registration views while checking the expected registry administrator. Both are nonconsuming and controlled by their `actor` argument, so a non-stakeholder application holding an explicit disclosure can confirm a credential inside its own transaction instead of using a plain stakeholder `fetch`.

The normative HTTP contract is [`openapi/credential-registry-v1.yaml`](openapi/credential-registry-v1.yaml), with canonical base path `/v1`. The intrinsic `/credentials` family reads `Credential` projections without requiring registration. The `/registered-credentials` family contains only contracts implementing both `Credential` and `RegisteredCredential`, joined by identical contract ID, and keeps `credential` and `registration` objects separate. This HTTP composition does not merge the Daml views or change `RegisteredCredential requires Credential`.

The contract is access-policy-neutral: deployments decide endpoint exposure, filtering, authentication, authorization, and audience. `/credential-registries` pages logical registries by distinct `registryAdmin` Party, uses that canonical Party string as `registryId`, and aggregates all active `CredentialRegistryFactory` projections for that administrator into sorted issuance-factory references. Active record retrieval is the baseline. Inactive retrieval and history require documented backing and separate event operations; unsupported requests must be rejected. The checked-in demo exposes both record families at `/v1`, supports snapshot-scoped active and archived records, and rejects separate event-history operations.

`CredentialView.credentialTypes : [Text]` is the compile-valid Daml field because `type` is a reserved keyword. PQS and raw Ledger API v2 retain LF-tagged values. The `/v1` HTTP read profile emits VC2-shaped `credential` objects for unsecured projections and original secured JSON for embedded proofs, or an `EnvelopedVerifiableCredential` with a `data:` compact ID for enveloped proofs. For ordinary projections it sets `@context` first entry `https://www.w3.org/ns/credentials/v2`, maps `credentialTypes` to `type` (requiring existing `VerifiableCredential`), flattens recursive claims and emits present identifier values as direct strings. `canton.holders` and `canton.anchorers` are envelope Party-string arrays, not VC core properties. Missing intrinsic bounds and subject IDs are omitted. Party and ContractId values remain ordinary strings, not invented DIDs. The demo Java API exposes separate `POST /v1/credential-verifications` for exact secured bytes (`application/vc+jwt` or embedded-proof `application/vc`), reporting narrow offline did:key EdDSA vc+jwt or eddsa-jcs-2022 verification and an independent local schema result; GET record families carry no calculated proof or schema result. Unsupported SD-JWT and COSE return `INDETERMINATE`. Daml validates only securing structure. Neither layer claims general W3C conformance, JSON-LD processing, remote resolution or external trust. See the CIP HTTP interface profile for constructor mapping and fail-closed rules.

Singular `GET /v1/credentials/{credentialId}?verify=true` and `GET /v1/registered-credentials/{credentialId}?verify=true` evaluate the stored secured document offline and return `{record,evaluation}`. Plain reads do not calculate verification, and both collection endpoints reject `verify=true` with HTTP 400. Standalone POST verification accepts supplied secured VC bytes without requiring registry presence.

Every `CredentialSubject` has `id : Optional W3C_VC_Identifier`. `Some identifier` serializes as `credentialSubject.id`; `None` omits that property and may still carry claims. Validation and identifier mapping apply only when the ID is present. Implementations must not infer subjects, holders, controllers, or authorization from identifiers, claims, or arbitrary values. `CredentialView.issuer` uses the same identifier representation while retaining distinct issuer semantics.

The DSO profile keeps `CredentialView.validUntil` and `RegisteredCredentialView.expiresAt` independent: either may be absent, and neither equality nor joint advancement is required. A future paid DSO extension changes only `expiresAt`, without renewing credential validity or changing claims. The demo choice implements no payment adapter; the retained `Renew` profile-authorization and payment-evidence inputs are unused and do not authorize or verify anything. A future extension profile must define authorization, payer, receiver, asset, pricing, payment-extension atomicity, replay and idempotency protection, failure and refund behavior, finality, concurrency control, privacy, metadata validation, and auditability.

### Snapshot collection contract

The next collection contract applies equally to `/v1/credentials` and `/v1/registered-credentials`: `state=active|archived|all` (default `active`); inclusive `createdFrom` and `archivedFrom`; exclusive `createdUntil` and `archivedUntil`; intrinsic filters `issuer`, `holder`, `credentialSubjectId`, and `keyPrefix`; and registered-only `registryAdmin`. `keyPrefix` matches claim keys within a single `CredentialSubject`, and combining it with `credentialSubjectId` requires both to hold on the same subject. Singular lookup selects active records by default, the latest archived record for `archived`, and active records before the latest archived record for `all`; duplicate active matches remain a conflict.

The requested response is `items`, `page`, `pageSize`, `hasNext`, `snapshotOffset`, and `nextPageToken`. A fresh request captures a snapshot and uses page-based OFFSET; token-only continuation uses keyset pagination; token plus page jumps within the same snapshot. Fetching one extra row determines `hasNext`. There is no separate snapshot token or observed-at field. Registry-list pagination remains unchanged and event-history endpoints remain unsupported.

`CredentialPageTokens` implements the independent HMAC-SHA256 signing and verification component, binding resource, snapshot, state, every filter, page size, next page, cursor, and expiry, with constant-time signature comparison and a minimum 32-byte secret. The listing manager canonicalizes timestamps, verifies tokens, validates their bigint PQS snapshot, and emits the next token only when an extra matching row exists. Configure a shared `CREDENTIALS_PAGINATION_SECRET` of at least 32 UTF-8 bytes and positive whole-second `CREDENTIALS_PAGINATION_TTL_SECONDS` (default 900).

PQS 3.5 supplies `set_latest(NULL)` returning the selected bigint offset, `validate_offset_exists(bigint)`, `active(name,bigint)`, `creates(name,0,bigint)`, and `archives(name,0,bigint)`. Registered joins require matching contract ID, creation event ID, offset and index; archived joins also require matching archive identity. JDBC maps composite event IDs to text and bigint fields without floating-point conversion. Readiness exercises all states and both projection families. See the SQL README for lifecycle columns and filter encoding.

The project uses Daml SDK `3.5.11` and targets LF `2.2`; the candidate source imports `AnyValue` from `splice-api-token-metadata-v1-1.0.0.dar`. The interface and model runtime packages do not depend on `daml-script`; only scripts/tests do. Build the Daml packages from `../demo` with:

```sh
make daml-build
make daml-test
```
