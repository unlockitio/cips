# Credentials and DID HTTP demo collection

Import `canton-network-credentials-and-did-demo.postman_collection.json` and `local-demo.postman_environment.json` into Postman (collection format v2.1). The intended consumer is an external integrator reading both demos' HTTP APIs. Folders 01–11 contain seeded GET examples, DID host fanout, four-host agreement and singular BFT reader checks. The separate Ledger API folder adds read-only auxiliary contract snapshots and explicitly opt-in Daml commands through Canton JSON Ledger API v2. It is a demo, not a conformance suite or a production mutation API.

From `cn-credentials-standard/demo`, launch the unified stack with `make build && make up`. This starts one Canton participant for both products, then both PQS projections, the Credentials API and all four DID APIs. Do not separately start the legacy DID Compose project. Check both `/q/health/ready` endpoints before running. Defaults are Credentials `http://localhost:41003`, DID `http://localhost:42003`, and `network=localnet`; change the environment bases if ports differ. Run the folders in numerical order: Credentials bootstrap captures a registry ID and Alice Party from the seeded name credential; DID bootstrap captures the runtime DSO DID, Party and the two name service URLs advertised by its DID document. Later requests depend on these captures. A fresh seed has 370 credential projections (360 deterministic, two names and eight scenarios) and a DSO DID. Pagination tokens are snapshot-bound and expire; rerun the first page before its continuation. The historical `createdFrom=2000-01-01T00:00:00Z` is an illustrative lower bound, not a claim about fixture creation time. Archived results can be empty.

Folder 09 is **opt-in**: `crossStackEnabled=false` skips its requests in a full run. To enable it, start the unified stack on `localnet` and run `make cross-stack-name-e2e` from `cn-credentials-standard/demo` to verify the same-participant fixture. The default Compose graph configures `CREDENTIALS_DID_ASSERTIONS_URL` to the internal DID API and seeds Alice's alias after the Credentials seed, using DemoHolderA as allocated on this very participant. The optional legacy DID-only seed has only `dso.canton`, not Alice. The DID cross-stack fixture also asserts `bob.canton` with the DSO Party, intentionally disagreeing with Bob's Credentials allocation, so the final 409 example depends on that seed. Set `crossStackEnabled=true` only after these prerequisites. Postman discovers the resolve and reverse URLs from the DSO DID service descriptors and calls them with `source=did`; it does not configure the Credentials API's assertion URL. The alias is a self-claim, not proof of ownership or name allocation.

Folder 08 checks name resolution and reverse resolution through all four DID hosts. The environment keeps `didBase=http://localhost:42003` for host 1 and adds `didBase2=http://localhost:42004`, `didBase3=http://localhost:42005`, and `didBase4=http://localhost:42006`. The DSO bootstrap verifies the four advertised endpoints in priority order 0–3 for each name service, keeps the first URLs for folder 09, and captures the full ordered lists as `discoveredResolveEndpoints` and `discoveredReverseEndpoints` JSON strings. Run folder 08 after folders 01 and 04; its first host captures `didFanoutAliceParty` for agreement checks on hosts 2–4. `didFanoutEnabled=true` by default because the unified stack starts all four; set it to `false` to skip the folder on a single-host deployment. These four DID hosts forward to **one Credentials authority**: they are not independent resolvers or a BFT quorum. Folder 09 remains separately opt-in with `crossStackEnabled=false` and its cross-stack fixture requirements above.

Folder 02 includes three seeded secured fixtures in both intrinsic and registered resource families, plus a structural placeholder negative. `external-did` returns an `EnvelopedVerifiableCredential` whose `id` is a `data:application/vc+jwt,<compact>` URL; the decoded signed document is not the top-level `credential`. `external-holderless` returns its original secured JSON with an embedded `eddsa-jcs-2022` proof. Both report `verification.status=VERIFIED` and `verification.schemaValidation.status=Success` for the local demo schema, separately from `registration` on registered reads. The base-credential placeholder reports `INDETERMINATE`, not `VERIFIED`. The seeded `external-tampered` vector projects score 86 with a proof signed over score 85 for its own ID. Its intrinsic and registered reads must report `FAILED` with `Invalid Data Integrity signature` and independent schema `Success`, without a typed projection mismatch. The older unseeded holderless tamper fixture remains for Java regression coverage. These assertions require the fixture validity window (2026-09-18 through 2030-09-18 UTC) and a freshly seeded stack. No remote DID/schema retrieval, status-list check, JSON-LD processing or W3C conformance is demonstrated. The seed selects the anchoring Party strictly: only a credential with a textual issuer **and** no Party holder **and** no Party subject is anchored by `DemoAnchorer`, so `urn:demo:scenario:external-holderless` reads back with empty `canton.holders`, no `credentialSubject[0].id` and a sole `DemoAnchorer` anchorer. `urn:demo:scenario:base-credential` also has a textual issuer but keeps a Party holder, so it stays anchored by `DemoIssuer`; this is the fixture rule, not an inference about external issuers in general. The anchorer is a Daml signatory, not proof that the textual issuer authorized anything. `urn:demo:scenario:expired-registration` is read twice to separate the two expiries: the intrinsic `/v1/credentials` view has no `registration` and keeps `credential.validUntil` in the future, while the `/v1/registered-credentials` view shows `registration.expiresAt` already in the past. Both remain `active`: registration expiry is registry metadata and does not archive the contract or invalidate the credential.

The DID demo's `/v1/credentials` and `/v1/credential-registries` return **discovery-only descriptors**, not Credentials API record pages. The two credential event-history routes are implemented but currently return 422 for unsupported history. Folders 10 and 11 exercise singular BFT reading and contain no fixed Canton Party IDs or tokens. Run folder 04 before 10 to capture the actual DSO DID; run folder 01 before 11. Folder 10 checks the DSO DID document on hosts 42003–42006 via bootstrap, intrinsic by-ID and registered by-ID reads; the exact `alsoKnownAs` array contains only `urn:fqpn:localnet:demo:dso.canton` under the default `network=localnet`, not Alice or Bob. This alias is self-asserted, not verified name ownership. It compares complete documents with object keys normalized while preserving array order, then checks the DID reader on 42007 for a validated 4-of-4 quorum. Folder 11 reads the same seeded intrinsic VC on Credentials hosts 41003–41006, compares complete canonical responses, and checks the singular Credentials reader on 41007 for a validated 4-of-4 result (3 required), plus a validated missing-ID 404. All four Credentials hosts share one PQS/Canton backend and do not establish independent fault domains. The BFT readers do not offer list or registered endpoints; this collection does not inject faults. The environment supplies distinct `credentialsBase2/3/4`, `credentialBftBase` and `didBftBase`; adjust them for remapped ports. Run each folder in order and do not mistake static JSON/script validation for an executed Newman run. Newman is optional and requires a running, seeded stack. Existing smoke and cross-stack E2E scripts remain the authoritative automated integration checks for the seeded GET journeys. They do not cover these interactive write journeys.

## Canton Ledger API v2: auxiliary reads and opt-in commands

Start and seed the unified stack first. Run the **Ledger API (writes and auxiliary contracts)** folder independently, not as part of a routine full-collection run. Its default `ledgerBaseUrl=http://localhost:41001` is the host mapping of the participant's container port 7575, distinct from the Credentials `/v1` read API at 41003 and gRPC at 41000. The folder's `GET /v2/version`, `GET /v2/parties`, `GET /v2/packages`, and `GET /v2/state/ledger-end` establish the runtime and capture seed Party IDs by unique hints. The preflight expects five seeded hints: `DemoIssuer`, `DemoHolderA`, `DemoHolderB`, `DemoAnchorer`, and `DSO`. A retained ledger seeded before `DemoAnchorer` was introduced fails this check; reseed a fresh project rather than editing the expectation. Verify the runtime schema at `GET {{ledgerBaseUrl}}/docs/openapi` if running a different Canton version. The request bodies here match the running 3.5.11 schema: tagged Daml variants (`{ "tag": "AV_Text", "value": "..." }`), optional values as JSON value or null, and `NonEmpty` as `{ "hd": ..., "tl": [] }`.

Run the first four preflight requests, then `ACS factory` to capture the issuer-anchored and registry-anchored factories. `ACS request`, `ACS holding`, and `ACS equity` inspect auxiliary templates; `ACS credential` reads intrinsic contracts with a bounded page (100). Repeat `ACS credential` while `credentialPageToken` is set to continue, and leave `ledgerOffset` unchanged until the page series ends. Refresh `Ledger end` to start a new snapshot and clear `credentialPageToken` before doing so. All ACS requests are **read-only HTTP POST** `/v2/state/active-contracts` (the credential page uses `/v2/state/active-contracts-page` to avoid oversized seed responses), filtered by template and visible Party. They are not auxiliary GET routes. An empty request/holding/equity snapshot is valid. An ACS result is an array of entries with `contractEntry.JsActiveContract.createdEvent`; a successful command uses `/v2/commands/submit-and-wait-for-transaction` and reads created contract IDs from `transaction.events[].CreatedEvent.contractId`, never from the offset-only submit-and-wait endpoint.

Writes are **skipped by default** by the folder's `pm.execution.skipRequest()` unless `ledgerWritesEnabled` is exactly `true`. This folder's read preflights still run in a full collection run; they require the Credentials participant. Run folders 01–09 separately if only the two `/v1` read demos are available. For a complete write run, set `ledgerWritesEnabled=true` only on a disposable local seeded ledger, run the preflights and factory snapshot, then execute `Submit Party credential issue`, `Submit external DID anchor`, `Submit name request`, `Submit name acceptance`, `Submit name holding`, and `Submit holding transfer by reissuance` in order, interleaving ACS reads as needed. The Party issuer issue acts as DemoIssuer and DemoHolderA; the external text issuer anchor acts as DemoIssuer and DemoHolderB, keeping DemoIssuer because it assigns a Party holder and Party subject, so it is outside the holderless DemoAnchorer fixture rule; acceptance acts as DSO and DemoHolderA through the registry-anchored factory. Name transfer acts as DSO, old owner DemoHolderA, and new owner DemoHolderB. `ACS credential` reads back the issued records; `ACS holding` reads the new owner and CID. A holder replacement is not required to demonstrate the distinct transfer by reissuance.

The seeded no-auth participant exposes the user `participant_admin`; an empty `ledgerUserId` selects it. Set `ledgerUserId` to an authorized user if your participant differs. If authentication is enabled, supply `ledgerToken` in your **private Postman environment** (or adjust local authorization); never export a real token into this checked-in file. This demo does not provision user rights. Each command uses a fresh GUID command ID, while `ledgerRunId` groups its logical IDs and canonical name (`postman-<runId>.canton`); the latter is created once during Party preflight and persists. Do not rerun a successful write: the collection refuses known captured duplicates, but a lost response or a cleared environment does not prove a submission failed. Inspect ACS and reconcile first. For a fresh independent run, clear captured `*CredentialId`, `nameRequestId`, `nameHoldingId`, `holdingOwner`, `credentialPageToken`, and `ledgerOffset`, clear `ledgerRunId`, then rerun parties and preflight; preserve the run ID when resuming a partial run. A repeated name can still be accepted because uniqueness is off-ledger registry responsibility. A successful command offset precedes PQS projection: retry the Credentials `/v1` GET after projection catches up, without resubmitting a write. The external DID issuer is only an anchored textual assertion, not verified DID authority, and DID aliases are self-claims, not name-allocation authority. No direct `DemoCredential` creation is offered.
