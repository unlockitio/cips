# Candidate Daml interfaces

This package contains directly consultable candidate interface source for the Canton Network DID Standard. It is interface-only: it is not a conforming DID registry, resolver, registrar, DID method registration, or deployment. It defines `DidDocument`, `RegisteredDidDocument`, and `DidRegistryFactory` in `Canton.Network.Did.V1`.

`Did` is an opaque `Text` wrapper. `DidDocumentView` separates intrinsic DID Document content from registration state and contains a non-empty controller set, verification methods and relationship references, and typed, versioned service endpoints. The candidate does not select method-specific validation, cryptographic suites, verification-material formats, JSON or JSON-LD contexts, external serialization or canonicalization, Party binding, controller or lifecycle authorization, or optional DID Core properties. It deliberately provides no generic archive or deactivate choice.

`RegisteredDidDocument` requires `DidDocument`. Its view returns the intrinsic `DidDocumentView` together with registry metadata: registry administrator, registration and update times, version ID, deactivation state and time, source, integrity and finality evidence, and extensible metadata. Concrete implementations must keep the returned document consistent with the required `DidDocument` view. `RegisteredDidDocument_PublicFetch` checks the caller-provided `expectedRegistryAdmin` against a known disclosed contract at transaction time. It is not anonymous discovery and does not independently prove DID control, current freshness, finality, external serialization, or HTTP caller identity. Concrete templates must establish the intended Canton visibility and stakeholder model.

`DidRegistryFactory_UpdateRegisteredDidDocuments` is a batch registration-metadata operation. Concrete implementations must authorize the actor, verify every target is owned by the registry, preserve intrinsic DID Document content unless a separately authorized lifecycle transition changes it, and reject inconsistent version, deactivation, time, source, integrity, finality, or authority metadata. A factory metadata update is a registry operation, not DID-controller authority.

Concrete implementations still need to define signatories and stakeholders; registration creation and removal; registry ownership; controller thresholds, delegation, recovery, rotation, and lifecycle transitions; Party-to-DID association; current and historical resolution; deactivation durability; metadata validation; visibility; source authentication; integrity, freshness, and finality verification; verification-material types and cryptographic suites; DID JSON or JSON-LD serialization and canonicalization; service-type registration and endpoint validation; and conflict, downgrade, migration, and failure behavior.

The normative local HTTP contract is [`openapi/did-v1.yaml`](openapi/did-v1.yaml). Its intrinsic `/dids` family reads only `DidDocument`; its `/registered-dids` family composes `DidDocument` and `RegisteredDidDocument` by identical contract ID and returns clear `did`, `didDocument`, and separate `registration` fields. Service responses preserve the Daml endpoint collection order and each endpoint's priority. The additional service-family names and discovery-only roots are demo-local vocabulary for topology preparation, not normative CIP semantics or claims of implemented credential and asset APIs. This HTTP composition does not alter or duplicate the separate Daml views. Direct collections support active, archived and all contract states at a validated PQS bigint snapshot, with lifecycle metadata, effective-time filters (`createdFrom`/`archivedFrom` inclusive `>=`, `createdUntil`/`archivedUntil` exclusive `<`) and HMAC nextPageToken pagination. Intervals with `From >= Until` are invalid; either archive filter excludes active rows. Registered historical joins additionally check event compatibility. Singular resolution and BFT remain active singular reads; historical collections do not imply historical singular resolution or independent quorum evidence.

The package uses Daml SDK `3.5.11` and LF target `2.2`. PQS `3.5.8` reporting embedded `daml-sdk.version` `3.5.2` does not require compiler patch equality: PQS consumes compiled Daml-LF packages and ledger events. LF `2.2` is the conservative stable target shared with PQS 3.5.8 defaults; LF `2.3` is intentionally deferred until its PQS projection and JSON behavior is explicitly certified.

From the parent `demo/` directory, `./scripts/fetch-dependencies.sh` downloads the Splice token metadata DAR from commit `fc5075093d9b10191aeedab66ff35cadaded9dc8` and verifies SHA-256 `455eb160cb5abd4ae9918a6fbb9dad471f721adda39f0e5c76feef08d05637fc`. The binary is stored only at the ignored canonical path `demo/.deps/splice-api-token-metadata-v1-1.0.0.dar`. Run `dpm build --all` from `demo/`; DAR files and build output are not checked in.

`daml/Canton/Network/Did/Test/V1Compile.daml` supplies compile/type fixtures for both interface views, the required-interface conversion from `RegisteredDidDocument` to `DidDocument`, the public-fetch choice, and factory batch updates. Actor/admin enforcement and update authorization are delegated to concrete template implementations, so runtime behavior tests require the concrete package in `../model` and scripts in `../test`.
